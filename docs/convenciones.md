# Convenciones — BitCode.Framework

Guía de convenciones para un proyecto consumidor del framework. Extraída de los patrones ya validados en `samples/Sample.Api` y en la suite de tests de cada fase — no son reglas nuevas, son las que el propio framework ya sigue.

## Estructura de un proyecto consumidor

```
MiApp/
  MiApp.Api/                      (o el nombre del proyecto Web)
    Program.cs                    (AddModules + UseModules, nada más)
    InfrastructureModule.cs       (envuelve los AddSharedX<T>() del framework)
    MiAppDbContext.cs             (: MultiTenantDbContext o MultiTenantIdentityDbContext)
    appsettings.json
    <Feature>/
      <Feature>.cs                 (entidad de dominio)
      Crear<Feature>Command.cs     (Command + Validator + Handler, un archivo o tres)
      Obtener<Feature>Query.cs     (Query + Handler)
      <Feature>Module.cs           (IWebFrameworkModule: MapGroup + endpoints)
```

Un feature = una carpeta = un `IWebFrameworkModule` con `[DependsOn(typeof(InfrastructureModule))]`. Ver `samples/Sample.Api/Productos/` como referencia completa.

## Nomenclatura

| Elemento | Convención | Ejemplo |
|---|---|---|
| Command | `{Verbo}{Entidad}Command` | `CrearProductoCommand`, `EliminarProductoCommand` |
| Query | `Obtener{Entidad}Query` / `Listar{Entidad}sQuery` | `ObtenerProductoQuery` |
| Validator | `{Command}Validator` | `CrearProductoCommandValidator` |
| Handler | `{Command}Handler` | `CrearProductoCommandHandler` |
| Response de Query | `{Entidad}Response` | `ProductoResponse` |
| Módulo de feature | `{Feature}Module` | `ProductosModule` |
| Error de dominio | `{Entidad}.{Motivo}` (código) | `"Producto.NoEncontrado"` |
| Permiso | `{entidad}.{accion}` (minúsculas, punto) | `"productos.crear"` |

## Reglas duras (no opcionales)

Derivadas de decisiones de diseño ya tomadas en fases anteriores — apartarse de ellas rompe garantías que el resto del framework asume:

1. **Un handler de un `ICommand` simple (sin `ITransactionalCommand`) nunca llama `IUnitOfWork.SaveChangesAsync` explícitamente.** `TransactionBehavior` ya lo hace al finalizar el pipeline con un `Result` exitoso. Ver el comentario en `CrearProductoCommandHandler` del piloto. Excepción explícita: un handler de `ITransactionalCommand` **sí** puede llamar `SaveChangesAsync` a mitad de su ejecución cuando necesita coordinar varias operaciones de escritura que dependen entre sí (por ejemplo, necesitar el resultado ya persistido de la primera antes de ejecutar la segunda) — todas esas llamadas intermedias quedan dentro de la misma transacción de base de datos abierta por `TransactionBehavior`, que revierte **todo** (incluidas las ya guardadas) ante un fallo posterior. `TransactionBehavior` mismo nunca llama `SaveChangesAsync` directamente: en el camino transaccional delega toda la persistencia final a un único `IUnitOfWork.CommitAsync` (F1-07).
2. **Un `IQuery` nunca modifica datos.** `TransactionBehavior` está restringido a `IBaseCommand` — una query que escribe no tiene la protección transaccional y puede dejar cambios a medias sin que el framework lo detecte.
3. **Solo un comando que implementa explícitamente `ITransactionalCommand` abre una transacción real de base de datos con rollback coordinado.** Un `ICommand`/`ICommand<T>` simple (sin `ITransactionalCommand`) persiste sus cambios automáticamente vía `SaveChangesAsync` al finalizar con éxito, pero **no** abre una transacción explícita — usalo para el caso común de un único agregado por comando. Reservá `ITransactionalCommand` para comandos que coordinan más de una operación de escritura (varios agregados, varios `SaveChanges`, efectos que deben confirmarse o revertirse en conjunto). Ver ADR `docs/adr/0009-contratos-comando-transaccion-explicita.md`. **(F1-07)** Mientras la transacción de un `ITransactionalCommand` está abierta, el handler no debe realizar llamadas HTTP salientes, a cache distribuido (Redis) ni a un futuro broker de eventos/mensajería — son fuente clásica de timeouts y deadlocks al mantener locks de base de datos abiertos durante una llamada de red lenta. Esas llamadas deben diferirse hasta después de que el `Result` exitoso confirme el commit (por ejemplo, publicando un evento de dominio vía Outbox — F1-23 — en lugar de llamar directamente a un broker dentro del handler).
4. **(F1-22) Un comando `IIdempotentCommand` exige una Idempotency-Key; sin ella se rechaza, nunca se ejecuta en silencio.** `IdempotencyBehavior` (registrado por `AddSharedApplication`, dentro del alcance de `TransactionBehavior` en el pipeline: Logging -> Validation -> Transaction -> Idempotency -> Handler) resuelve la clave vía `IIdempotencyKeyProvider` (Shared.Domain) — nunca es un campo del comando. Un proyecto con pipeline HTTP llama `services.AddHttpContextIdempotencyKeyProvider()` (Shared.Infrastructure.Web) ANTES de `AddSharedApplication` para que la clave se lea del header `Idempotency-Key` del request (mismo patrón que `AddHttpContextTenantProvider`); sin ese registro, `NullIdempotencyKeyProvider` (default, `TryAddScoped`) siempre devuelve `null` y todo `IIdempotentCommand` se rechaza con `Idempotency.KeyRequired` (400). Con una clave ya usada por un request con el MISMO payload (comparado por SHA-256 del comando serializado), el handler no se vuelve a ejecutar: se devuelve el mismo `Result` exitoso ya obtenido, sin duplicar el efecto de negocio. Con la misma clave y un payload DISTINTO, se rechaza con `Idempotency.KeyReused` (409) en vez de tratarse como el mismo reintento. Solo un `Result` exitoso queda guardado (tabla `IdempotencyKeys`, EF Core, `ITenantEntity` — dos tenants nunca colisionan por reutilizar la misma clave literal); un `Result.Failure` o una excepción no dejan rastro, así que un reintento posterior a un fallo ejecuta el handler con normalidad. El registro de idempotencia se persiste en el mismo `SaveChangesAsync`/transacción que el efecto del comando (por eso `IdempotencyBehavior` corre DENTRO de `TransactionBehavior`, no antes): un fallo a mitad de camino nunca deja el registro sin el efecto real, ni al revés. Cada entrada vence (`RetentionPeriod` de `IdempotencyOptions`, 24 horas por defecto, configurable en `AddSharedApplication`); `IIdempotencyStore.PurgeExpiredAsync` hace la limpieza física en bloque y está pensado para invocarse desde un job periódico (p. ej. un `IJob` de Quartz.NET registrado con `AddSharedBackgroundJobs`, ver Fase 4) — esta tarea no incluye scheduling automático. Ver `samples/Sample.Api/Productos/CrearProductoCommand.cs` (referencia de uso end-to-end, sin ningún cambio de endpoint) y `tests/Shared.Infrastructure.Persistence.Tests/Integration/IdempotencyBehaviorIntegrationTests.cs`/`samples/Sample.Api.Tests/Integration/ProductosEndpointsIntegrationTests.cs` (criterio de aceptación "POST repetido no duplica operación", contra SQL Server real).
5. **`IUnitOfWork`/`DbContext` son propiedad exclusiva del pipeline (`TransactionBehavior`/`UnitOfWork`); nada más llama `Database.BeginTransactionAsync`/`IDbContextTransaction.CommitAsync`/`RollbackAsync` directamente**, y ningún handler ni repositorio recibe un `DbContext` inyectado (solo `IRepository<T, TId>`/`IUnitOfWork`). **(F1-09)** Si un handler de `ITransactionalCommand` despacha otro `ITransactionalCommand` vía `ISender` dentro del mismo scope (mismo `IUnitOfWork`/`DbContext`), ambos comparten la misma transacción física: solo el `BeginTransactionAsync`/`CommitAsync` del nivel más externo abre/confirma la transacción; los niveles internos reutilizan la transacción existente y su `CommitAsync` solo hace `flush` (`SaveChangesAsync`) sin cerrarla. Un `RollbackAsync`, sea del nivel interno o externo, siempre revierte la transacción física completa — no existe "rollback parcial" de un nivel anidado, porque ambos comandos comparten el mismo `ChangeTracker`. Ver addendum F1-09 en `docs/adr/0009-contratos-comando-transaccion-explicita.md`.
5. **Nunca exponer `IQueryable` desde un repositorio.** Toda consulta pasa por `ISpecification<T>` o por los métodos tipados de `IRepository`/`IReadRepository`.
15. **(F1-17) Un handler de `IQuery` inyecta `IReadRepository<TEntity, TId>`, nunca `IRepository<TEntity, TId>`.** `IReadRepository<,>` resuelve a `ReadOnlyRepositoryBase<,>` (Shared.Infrastructure.Persistence), que fuerza `AsNoTracking()` en toda lectura (`GetByIdAsync`, `ListAsync`, proyecciones, paginación) sin depender de que cada `ISpecification` declare `ApplyAsNoTracking()` — coherente con la regla dura #2 (un `IQuery` nunca muta, así que el `ChangeTracker` no aporta nada). `IRepository<,>` (resuelto a `RepositoryBase<,>`) sigue trackeando por defecto: el lado de escritura necesita `GetByIdAsync` trackeado para poder llamar `Update` sobre la misma instancia. Si el resultado de un `IQuery` es un DTO y no la entidad completa, usar el overload de `ListAsync`/`ListPagedAsync` con un `selector` (`Expression<Func<TEntity, TResult>>`) en vez de traer la entidad completa y proyectar en memoria — el `SELECT` generado por EF Core solo trae las columnas usadas por el `selector`. Para un listado paginado, usar `IReadRepository<,>.ListPagedAsync`/`ListPagedAsync<TResult>` (devuelven `PagedResult<T>`, Shared.Kernel) en vez de un `CountAsync` + `ListAsync` manual: ambas consultas comparten el mismo filtro de la especificación sin traer todas las filas a memoria solo para contarlas. Ver `docs/guia-queries-eficientes.md`.
6. **Un error de negocio esperado es un `Result.Failure`, nunca una excepción.** Las excepciones son para lo verdaderamente inesperado; `GlobalExceptionHandler` las trata como error 500 sin distinción, salvo `OperationCanceledException` con el request abortado (regla 10).
10. **(F1-10) Todo método async en la cadena de un comando/query acepta y propaga un `CancellationToken`; nunca `CancellationToken.None` salvo justificación explícita en un comentario.** Esto incluye el endpoint (`CancellationToken ct` inyectado por el binding de minimal API, tomado de `HttpContext.RequestAborted`), `ISender.Send(request, ct)`, cada `IPipelineBehavior` del pipeline de MediatR, el handler, `IRepository`/`IReadRepository` y `IUnitOfWork`. La única excepción legítima es cuando el propio contrato de una API de terceros no acepta `CancellationToken` (por ejemplo, `UserManager`/`RoleManager` de ASP.NET Core Identity en `PermissionService`) — ahí no hay nada que propagar. Una cancelación (`OperationCanceledException`/`TaskCanceledException`) **nunca** se traduce a un `Result.Failure`/ProblemDetails como si fuera un error de negocio o una excepción inesperada:
    - `TransactionBehavior` revierte la transacción de un `ITransactionalCommand` ante una cancelación igual que ante cualquier otro fallo (para no dejar bloqueos de fila huérfanos en SQL Server), pero relanza la excepción tal cual — nunca la atrapa como el `catch (Exception)` genérico ni la convierte en un `Result.Failure`. El `RollbackAsync` de ese camino se invoca con `CancellationToken.None`, no con el token ya cancelado: pasarle el token cancelado haría que EF Core lance `OperationCanceledException` al iniciar el propio rollback sin llegar a emitir el `ROLLBACK` real contra SQL Server.
    - `GlobalExceptionHandler` no trata una `OperationCanceledException` con `httpContext.RequestAborted.IsCancellationRequested == true` como error 500: la loguea en un nivel bajo y no intenta escribir una respuesta sobre una conexión que el cliente ya cerró.
    - Ver `TransactionBehaviorTests` (unitarios) y `CancellationIntegrationTests` (SQL Server real) en `Shared.Application.Tests`/`Shared.Infrastructure.Persistence.Tests` para el criterio de aceptación "requests cancelados liberan recursos": una escritura posterior sobre la misma fila, desde una conexión nueva, tiene éxito de inmediato después de la cancelación (no queda ningún bloqueo colgado).
11. **(F1-10) `AddSharedPersistence<TContext>` acepta opcionalmente un `Action<PersistenceOptions>` con `CommandTimeoutSeconds`** para acotar cuánto puede tardar un comando SQL individual en el servidor, independiente del `CancellationToken` del request (protege contra, por ejemplo, un bloqueo inesperado en SQL Server que el cliente nunca cancela). Sin configurar, se mantiene el default del proveedor de EF Core para SQL Server (equivalente al de `SqlCommand`, 30 segundos) — no es un comportamiento nuevo, es la posibilidad de ajustarlo por proyecto.
7. **Toda entidad que necesite auditoría/soft-delete/multi-tenancy implementa la interfaz correspondiente (`IAuditedEntity`/`ISoftDelete`/`ITenantEntity`) y nada más** — el framework detecta las interfaces por reflexión, no requiere configuración adicional en `OnModelCreating`.
8. **Un endpoint siempre termina en `.ToOkOrProblem()` o `.ToProblemDetails()` sobre el `Result` que devuelve el `Sender`**, nunca inspeccionando manualmente `IsSuccess`/`Error` para construir la respuesta HTTP a mano.
12. **(F1-12) El `TenantId` de un `ITenantProvider` productivo nunca se resuelve desde un header HTTP, query string o cualquier dato que el cliente controle directamente sin pasar por autenticación validada por el servidor.** Un proyecto multi-tenant real registra `services.AddHttpContextTenantProvider()` (Shared.Infrastructure.Web) ANTES de `AddSharedPersistence<TContext>()` en su `InfrastructureModule` — resuelve el tenant desde el claim `TenantClaimTypes.TenantId` del JWT ya validado (`HttpContext.User`), emitido automáticamente por `JwtTokenGenerator` a partir de `ApplicationUser.TenantId`. Si un usuario autenticado no trae ese claim, `HttpContextTenantProvider` lanza `TenantResolutionException` en vez de asumir un tenant por defecto o deshabilitar el filtro — fallar de forma segura es preferible a arriesgar una fuga de datos entre tenants (ver `docs/threat-model.md`, hallazgo S2, y ADR `docs/adr/0003-tenancy-multi-tenant-por-filtro-global.md`). `NullTenantProvider` (registrado por defecto vía `TryAddScoped`) sigue siendo la opción correcta solo para proyectos de un único tenant o para código sin `HttpContext` (jobs en background, seeders) — nunca para un proyecto multi-tenant real con pipeline HTTP.
9. **Una entidad con concurrencia optimista implementa `IHasConcurrencyToken` (propiedad `byte[] RowVersion`) y nada más** — el framework la detecta por reflexión (mismo patrón que `IAuditedEntity`/`ISoftDelete`/`ITenantEntity`) y configura `RowVersion` como token de concurrencia de EF Core (`IsRowVersion()`) sin configuración adicional en `OnModelCreating`. `TransactionBehavior` captura de forma uniforme el conflicto resultante (`DbUpdateConcurrencyException` de EF Core, traducido primero a `ConcurrencyConflictException` en `Shared.Domain` para no filtrar el tipo de EF Core hasta la capa de aplicación) y lo convierte siempre en el mismo `Result.Failure` con `ConcurrencyError.Conflict` (código `"Concurrency.Conflict"`, `ErrorType.Conflict`) — nunca en una excepción sin controlar que llegue a `GlobalExceptionHandler`. `ResultExtensions.ToProblemDetails` ya mapea `ErrorType.Conflict` a `409 Conflict` (F1-08).
13. **(F1-15) `ITenantContext` (Shared.Domain) es el contrato que debe consumir código de aplicación/logging para leer el `TenantId` del request actual — no `ITenantProvider` directamente.** `ITenantContext` envuelve el `ITenantProvider` ya registrado y memoiza el `TenantId` la primera vez que se accede dentro del scope: una vez resuelto, ningún handler, middleware o dependencia puede sobrescribirlo (la interfaz no expone ningún setter). `ITenantProvider` sigue siendo el contrato de bajo nivel que consumen `MultiTenantDbContext`/`TenantSaveChangesInterceptor` para el filtro global de EF Core (F1-12) — no cambia. `AddSharedPersistence<TContext>` registra `TenantContext` (implementación por defecto) con `TryAddScoped`, igual que el resto de los contratos de tenancy. Un proyecto con pipeline HTTP que quiera que el `TenantId` aparezca automáticamente en todos los logs estructurados del request (sin agregarlo a mano en cada `ILogger.LogInformation(...)`) llama `app.UseTenantContextLogging()` (Shared.Infrastructure.Web, `TenantContextApplicationBuilderExtensions`) después de `UseAuthentication()`/`UseAuthorization()` — el middleware empuja el `TenantId` al `LogContext` de Serilog (`Enrich.FromLogContext()`, ya configurado por `UseSharedSerilog`) para todo el resto del pipeline, y lo retira automáticamente al finalizar el request (no se filtra entre requests concurrentes ni a código fuera del pipeline).
16. **(F1-21) Ningún endpoint de listado queda ilimitado: `page`/`pageSize` crudos del cliente siempre pasan por `PageRequest.Create` (Shared.Kernel) antes de llegar a `IReadRepository<,>.ListPagedAsync`.** `PageRequest.Create(page, pageSize, maxPageSize = 100)` es el punto de validación principal — un `pageSize` fuera de rango (`<= 0` o mayor al máximo configurable, 100 por defecto) nunca se trunca en silencio: devuelve un `Result<PageRequest>` fallido con `ErrorType.Validation` (`"Paginacion.TamanioInvalido"`/`"Paginacion.TamanioExcedeLimite"`) que el handler de `IQuery` propaga como el `Error` de su propio `Result`, sin ejecutar ninguna consulta. `IReadRepository<,>` agrega overloads de `ListPagedAsync`/`ListPagedAsync<TResult>` que reciben directamente un `PageRequest`. `RepositoryBase.NormalizePaging` (usado por los overloads con `page`/`pageSize` crudos) aplica el mismo máximo como recorte defensivo de última línea — pero ese recorte sí trunca en silencio a propósito (protege la base de datos si algo bypasea `PageRequest`), no es el mecanismo de validación que debe usar un endpoint. `ListAsync()`/`ListAsync(spec)` sin paginar (colección completa) solo es aceptable cuando el volumen está estructuralmente acotado por diseño (catálogo de configuración pequeño y fijo, relación 1:1 con el tenant) — nunca para una tabla que crece sin límite con la actividad del negocio; para cualquier otro caso, usar `ListPagedAsync`. No se implementa paginación por cursor (keyset) todavía — decisión consciente documentada en `docs/guia-queries-eficientes.md` (sección "Límites máximos de paginación"): el volumen actual de los consumidores del framework no justifica el costo de una primitiva nueva; revisar si un consumidor real reporta "page drift" o degradación de `Skip`/`Take` en tablas grandes. Ver `docs/guia-queries-eficientes.md` y `samples/Sample.Api/Productos/ListarProductosQuery.cs`.
14. **(F1-16) Cachear datos sensibles a tenant con `HybridCache` directamente (sin componer el `TenantId` en la clave) es una fuga de información entre tenants, no un detalle de implementación.** `HybridCache` no tiene ningún concepto de tenant propio: dos tenants que pidan el mismo recurso lógico ("producto con slug X") con la misma clave literal reciben el mismo valor cacheado. Un handler que cachee el resultado de una query de negocio debe usar `ITenantAwareCache` (Shared.Infrastructure.Caching, registrado por `AddSharedCaching` vía `TryAddScoped`), que compone `"tenant:{TenantId}:"` en la clave efectiva usando `ITenantContext` (F1-15) y lanza `TenantResolutionException` (fallar de forma segura, mismo principio que `HttpContextTenantProvider`) si el proyecto opera en modo multi-tenant sin un `TenantId` resuelto para el scope actual. `HybridCache` directamente sigue siendo correcto solo para datos que **no** son sensibles a tenant (metadata/configuración compartida entre todos los tenants). Ver `docs/threat-model.md` (hallazgo I5) y `docs/adr/0006-cache-hybridcache-valkey-redis.md`.
17. **(F1-23) Un agregado que necesita notificar un hecho de negocio a otros módulos/bounded contexts levanta un `DomainEvent` (Shared.Kernel) con `RaiseDomainEvent` dentro de su propio constructor o método de negocio — nunca llama directamente a un broker de mensajería ni a `IUnitOfWork.SaveChangesAsync` para "asegurar" que el evento se guarde.** Para que el interceptor lo recolecte, la entidad debe heredar de `AggregateRoot<TId>` (no alcanza con `Entity<TId>` simple): `AggregateRoot<TId>` implementa `IHasDomainEvents`, el contrato no genérico que `OutboxSaveChangesInterceptor` (Shared.Infrastructure.Persistence, registrado por `AddSharedPersistence<TContext>`) usa para recorrer `ChangeTracker.Entries<IHasDomainEvents>()` sin importar el tipo del identificador del agregado. Ese interceptor serializa cada evento pendiente (`JsonSerializer.Serialize(domainEvent, domainEvent.GetType())`) y lo agrega como fila `OutboxMessage` (Shared.Domain, `ITenantEntity`) al mismo `ChangeTracker`, dentro del MISMO `SaveChangesAsync`/transacción que persiste el cambio de negocio del agregado — nunca en una escritura separada. Esto es lo que garantiza el criterio de aceptación de F1-23 ("evento no se pierde tras commit"): si el commit tiene éxito, el evento ya está en la base junto con el cambio de negocio; si la transacción hace rollback (por ejemplo, un `ITransactionalCommand` cuyo paso posterior falla, F1-07/F1-09), ninguno de los dos queda persistido, aunque ambos ya se hubieran enviado a SQL Server en un `SaveChangesAsync` intermedio. `OutboxMessage.ProcessedAtUtc` queda siempre en `null` tras esta tarea — el relay/publisher que lea las filas pendientes y las publique a un broker externo (Kafka, ADR `docs/adr/0005-mensajeria-kafka.md`, todavía `Proposed`) es trabajo de Fase 3, condicionado a la aprobación humana de ese ADR; F1-23 no lo implementa. Ver `tests/Shared.Infrastructure.Persistence.Tests/Integration/OutboxIntegrationTests.cs` (criterio de aceptación verificado contra SQL Server real, incluida la atomicidad ante rollback).
18. **(F1-24) Un futuro consumidor real de mensajería (Fase 3) invoca `IInboxMessageProcessor.ProcessAsync(messageId, messageType, payload, handler)` (Shared.Application, registrado por `AddSharedApplication`) una vez por cada mensaje entregado por el broker, ANTES de reconocer/hacer commit del offset — nunca ejecuta el efecto de negocio del mensaje "a mano" fuera de este mecanismo.** `messageId` es el identificador único que trae el mensaje original (por ejemplo, clave de partición + offset de Kafka, o cualquier identificador de negocio único que el productor incluya) — es la clave de deduplicación contra `InboxMessage` (Shared.Domain, `ITenantEntity`, índice único `(TenantId, MessageId)` en `InboxModelConfigurator`). Si ya existe una fila con `ProcessedAtUtc` no nulo para ese `messageId`, `ProcessAsync` devuelve `InboxProcessOutcome.Discarded` sin ejecutar `handler` — este es el criterio de aceptación literal de F1-24 ("duplicados descartados"), necesario porque un broker como Kafka entrega mensajes "at-least-once" (el mismo mensaje puede llegar más de una vez; el Plan Maestro, sección 3.2, prohíbe prometer exactly-once de punta a punta en mensajería). `handler` debe modificar el estado a través del mismo `DbContext`/`IUnitOfWork` de scope (por ejemplo, vía `IRepository`) sin llamar a `SaveChangesAsync` por su cuenta: `InboxMessageProcessor` llama a `SaveChangesAsync` UNA sola vez, después de que `handler` termina con éxito, persistiendo atómicamente tanto el efecto de negocio como la marca `ProcessedAtUtc` del mensaje — mismo patrón de atomicidad que `OutboxSaveChangesInterceptor` (F1-23) e `IdempotencyBehavior` (F1-22). Si `handler` lanza una excepción, `InboxMessageProcessor` nunca llega a esa llamada: ninguna fila de `InboxMessage` queda persistida para ese intento, así que un reintento posterior con el MISMO `messageId` no se trata como duplicado — encuentra que no existe ningún registro y vuelve a ejecutar `handler` con normalidad (distinto de un duplicado real, que sí tiene una fila con `ProcessedAtUtc` no nulo). `InboxMessage.RetryCount`/`Error` quedan reservados para un futuro consumidor que decida persistir explícitamente sus intentos fallidos (por ejemplo, para una cola de mensajes muertos/DLQ); F1-24 no los escribe desde ningún camino de fallo, mismo criterio que `OutboxMessage.RetryCount`/`Error` en F1-23. Esta tarea NO implementa ningún consumidor real de Kafka ni ninguna suscripción a un broker (Fase 3, ADR `docs/adr/0005-mensajeria-kafka.md`, todavía `Proposed`) — solo el mecanismo genérico y reutilizable, independiente del formato de mensaje concreto. Riesgo conocido (no cubierto por el criterio de aceptación literal, mismo tipo de trade-off que F1-22 documenta para `IdempotencyBehavior`): dos llamadas concurrentes con el mismo `messageId` que todavía no persistió ninguna fila pueden ejecutar `handler` dos veces en paralelo; el índice único evita que ambas persistan, pero la segunda falla con una excepción sin traducir en vez de resolver a un "cache hit". Ver `tests/Shared.Infrastructure.Persistence.Tests/Integration/InboxIntegrationTests.cs` (ambos casos verificados contra SQL Server real).

19. **(F1-26) Un `HttpClient` saliente nuevo hacia un servicio externo se registra con `services.AddResilientHttpClient<TClient>(...)` (Shared.Infrastructure.Http), nunca con `AddHttpClient<TClient>()` directo.** `AddResilientHttpClient` compone, sobre `Microsoft.Extensions.Http.Resilience` (Polly v8, el mecanismo estándar de .NET para `IHttpClientFactory`, no una implementación propia): timeout por intento y total, retry con backoff exponencial y jitter siempre activo (mitiga "thundering herd" entre instancias), circuit breaker y un limitador de concurrencia (bulkhead) — todos configurables vía `HttpResilienceOptions` (código o `IConfiguration`). La pieza que **no** es configurable, porque es una garantía dura y no un parámetro de afinación, es el predicado de retry: `HttpRetrySafety.IsSafeToRetry` (`Shared.Infrastructure.Http.Resilience`) solo permite reintento automático para `GET`/`HEAD`/`PUT`/`DELETE` (idempotentes por RFC 9110) — un `POST`/`PATCH` NUNCA se reintenta por defecto, aunque el servicio externo responda un código transitorio (503), porque repetirlo sin garantía de idempotencia del receptor puede duplicar un efecto de negocio. Un `POST`/`PATCH` puntual que el llamador sabe que el servicio externo deduplica se marca explícitamente con `HttpRequestMessage.MarkSafeToRetry()` o incluyendo el header `Idempotency-Key` (mismo nombre que el header de `IIdempotentCommand` del lado entrante, F1-22, aunque sin relación de implementación entre ambos) — sin esa marca, el request se deja tal cual ante una falla, nunca se reintenta en silencio. Esta tarea prepara el mecanismo reutilizable para un futuro consumidor real (Fase 2+): hoy ningún módulo del framework ni `samples/Sample.Api` declara un `HttpClient` saliente propio. No confundir con F1-10 (timeouts de operaciones de **base de datos**, `PersistenceOptions.CommandTimeoutSeconds`) ni con rate limiting del lado servidor (fuera de alcance) — ambos son mecanismos distintos. Ver `docs/guia-resiliencia-http.md` y ADR `docs/adr/0013-resiliencia-http-saliente-microsoft-extensions-http-resilience.md`.
18. **(F1-25) Un check de disponibilidad de una dependencia externa crítica (SQL Server, Redis, un broker, un servicio de terceros) va SIEMPRE con el tag `"ready"` y nunca se agrega a `/health/live`.** `/health/live` (Shared.Infrastructure.Web, `MapSharedHealthChecks`) usa un `Predicate` que descarta todos los checks registrados — nunca ejecuta ningún delegado, ni siquiera para reportarlo como fallido — porque el proceso .NET puede estar perfectamente sano aunque una dependencia externa esté caída, y un orquestador que interprete eso como liveness reiniciaría el proceso sin necesidad (un restart no arregla que SQL Server no responda). `/health/ready` solo ejecuta los checks etiquetados `"ready"` y responde 503 si alguno falla, para que un balanceador/orquestador saque la instancia del pool de tráfico hasta que la dependencia se recupere. `AddSharedPersistence<TContext>` (SQL Server, `Database.CanConnectAsync`) y `AddSharedCaching` (Redis, si `Caching:RedisConnectionString` está configurado) ya registran su propio check `"ready"` — un módulo de plataforma nuevo que dependa de otra infraestructura crítica sigue el mismo patrón. Ver `docs/guia-health-checks.md`.
21. **(F1-28) Un endpoint Minimal API que retorna `Task<IResult>` (nunca `Results<T1, T2, ...>`) anota explícitamente cada respuesta posible con `.Produces<T>(statusCode)`/`.ProducesProblem(statusCode)`/`.ProducesValidationProblem(statusCode)` — el generador nativo de OpenAPI (`Microsoft.AspNetCore.OpenApi`, F1-28) no puede inferir status codes/schemas por reflexión de un delegado que retorna `IResult` genérico.** `services.AddSharedOpenApiForApiVersion(majorVersion, configureOptions?)` (`Shared.Infrastructure.Web.OpenApi`) registra un documento OpenAPI **separado por cada versión mayor** de API HTTP (F1-27) — `/openapi/v{N}.json`, mapeado por un único `app.MapOpenApi()` — nunca uno mezclando los contratos de dos versiones: el filtro (`OpenApiOptions.ShouldInclude`) reconoce la `ApiVersionMetadata` que `Asp.Versioning.Http` adjunta a cada endpoint (`.HasApiVersion(...)`/`.MapToApiVersion(...)`), y documenta en TODOS los documentos a un endpoint sin esa metadata (version-neutral). Límite real verificado (no un bug del filtro): `/health/live`/`/health/ready` (`MapHealthChecks`, F1-25) no aparecen en NINGÚN documento, porque ese método no pasa por `RequestDelegateFactory` y el generador nunca llega a construir una `ApiDescription` para ellos — son endpoints operativos, no parte del contrato de negocio versionado. Un proyecto que proteja al menos un endpoint con `RequireAuthorization`/`[Authorize]` encadena `.AddJwtBearerSecurityScheme()` (`OpenApiSecuritySchemeOptionsExtensions`) al configurar el documento — nunca describir un esquema de seguridad que el servidor no exige en ningún endpoint (contrato engañoso): `samples/Sample.Api` no lo llama a propósito, porque hoy ninguno de sus endpoints usa autenticación real. Ver `docs/guia-openapi.md` y `samples/Sample.Api.Tests/Integration/OpenApiDocumentsIntegrationTests.cs` (criterio de aceptación "Validación automática": cada documento generado en tiempo de ejecución se parsea con `Microsoft.OpenApi.Reader.OpenApiDocument.Parse` contra SQL Server real, no un archivo estático ni una inspección visual).
20. **(F1-27) Todo endpoint HTTP público se expone bajo un segmento de versión de ruta, `/api/v{mayor}/...`, nunca sin versión.** `services.AddSharedApiVersioning()` (Shared.Infrastructure.Web, `Asp.Versioning.Http`) configura `UrlSegmentApiVersionReader` como único mecanismo de lectura de versión (nunca header ni media type, decisión ya fundamentada en `docs/politica-versionado.md`, sección 4) y `AssumeDefaultVersionWhenUnspecified = false` — un request sin segmento de versión no matchea ningún endpoint. Cada módulo construye su propio `ApiVersionSet` (`app.NewApiVersionSet().HasApiVersion(...)...Build()`) y lo aplica a su grupo de rutas con `.WithApiVersionSet(...)`; un endpoint nuevo que agrega un contrato breaking se mapea con `.MapToApiVersion(...)` bajo una versión mayor nueva **junto a** la anterior (que sigue mapeada con `.HasApiVersion(...)` sin cambios), nunca reemplazándola en el mismo path. Deprecar una versión es `HasDeprecatedApiVersion(...)` en el `ApiVersionSet` (no saca la versión de servicio; solo agrega el header de reporte `api-deprecated-versions` a las respuestas, junto con `api-supported-versions` para las vigentes vía `ReportApiVersions = true`) — **no** son los headers IETF `Sunset`/`Deprecation`, ver `docs/guia-versionado-api.md` para la aclaración completa. Pedir una versión no declarada por ningún endpoint responde 404 (el 404 estándar de enrutamiento: no queda ningún endpoint candidato para esa combinación de ruta+versión), verificado contra el servidor real, no un 400 asumido de antemano. Ver `samples/Sample.Api/Productos/ProductosModule.cs` (v1 deprecada + v2 coexistiendo sobre el mismo grupo de rutas) y `samples/Sample.Api.Tests/Integration/ApiVersioningIntegrationTests.cs` (criterio de aceptación "versiones coexistentes", verificado contra SQL Server real).

## Cuándo usar qué

| Necesito... | Uso |
|---|---|
| Una entidad nueva | `dotnet new bitcode-entity -n MiEntidad --MultiTenant true\|false` |
| Un feature CQRS nuevo | `dotnet new bitcode-feature -n MiAccion` |
| Agrupar servicios de una feature | `IFrameworkModule` con `[DependsOn(typeof(InfrastructureModule))]` |
| Que el módulo también mapee endpoints | `IWebFrameworkModule` en vez de `IFrameworkModule` |
| Cachear el resultado de una query costosa **sensible a tenant** (datos de negocio) | `ITenantAwareCache.GetOrCreateAsync` (F1-16, Shared.Infrastructure.Caching) — nunca `HybridCache` directamente: compone el `TenantId` en la clave para que dos tenants nunca compartan una entrada por usar la misma clave lógica. Recordar que la escritura a Redis L2 es asíncrona, no asumir consistencia inmediata entre instancias |
| Cachear datos que **no** son sensibles a tenant (metadata/configuración global compartida) | `HybridCache.GetOrCreateAsync` directo (Fase 4) — acá sí es correcto que todos los tenants compartan la misma entrada |
| Un job recurrente | `IJob` de Quartz.NET registrado en `AddSharedBackgroundJobs` |
| Proteger un endpoint por permiso | `[RequirePermission("entidad.accion")]` o `.RequireAuthorization("entidad.accion")` — funciona tanto con `AddSharedSecurity` (JWT propio) como con `AddSharedOidcAuthentication` (F2-01), ambos registran `AddSharedPermissionEvaluation` (F2-07). Ver `docs/guia-rbac-2.md` |
| Saber por qué un sujeto puede (o no) ejercer un permiso (trazabilidad, auditoría) | Inyectar `IPermissionEvaluator` (F2-07, Shared.Infrastructure.Security.Permissions) e inspeccionar `EffectivePermissions.Grants` (`PermissionGrant.Source`) — nunca reconstruir manualmente qué rol/claim lo originó. Ver `docs/guia-rbac-2.md` |
| Autorizar una operación por atributos de negocio de la instancia concreta del recurso (monto, empresa, sucursal), además del permiso RBAC | Inyectar `IAuthorizationPolicyEvaluator` (F2-08, Shared.Infrastructure.Security.Abac) desde el handler (después de leer la entidad) y llamar `EvaluateAsync(principal, new AbacResource(tipo, atributos), accion)` — nunca resolver esto a mano comparando claims contra la entidad. Se invoca explícitamente, no es declarativo como `[RequirePermission]`: los atributos del recurso solo se conocen en tiempo de ejecución. Ver `docs/guia-abac.md` |
| Resolver el tenant en un proyecto multi-tenant real | `services.AddHttpContextTenantProvider()` (Shared.Infrastructure.Web) antes de `AddSharedPersistence<TContext>()` — nunca implementar `ITenantProvider` leyendo un header/query string |
| Leer el `TenantId` del request actual desde un handler/servicio de aplicación | Inyectar `ITenantContext` (Shared.Domain), no `ITenantProvider` — ya viene memoizado e inmutable para el scope |
| Que el `TenantId` aparezca automáticamente en todos los logs de un request | `app.UseTenantContextLogging()` (Shared.Infrastructure.Web) después de `UseAuthentication()`/`UseAuthorization()` |
| Un listado de solo lectura para un `IQuery` (grilla, combo, export) | `IReadRepository<,>.ListAsync(spec, selector)` (proyección a DTO) o `.ListPagedAsync(spec, selector, page, pageSize)` (paginado) — nunca traer la entidad completa si solo se necesitan algunas columnas. Ver `docs/guia-queries-eficientes.md` (F1-17) |
| Un listado paginado expuesto a un endpoint HTTP | Construir un `PageRequest` con `PageRequest.Create(page, pageSize)` (Shared.Kernel, F1-21) en el handler, y pasarlo al overload de `IReadRepository<,>.ListPagedAsync(spec, selector, pageRequest, ct)` — nunca pasar `page`/`pageSize` crudos del cliente sin validar (un `pageSize` fuera de rango devuelve `Result.Failure` en vez de truncarse en silencio). Ver `docs/guia-queries-eficientes.md` y `samples/Sample.Api/Productos/ListarProductosQuery.cs` |
| Un agregado (`SUM`/`COUNT` combinados, etc.) o una consulta que `ISpecification<T>` no expresa bien | `IHotPathQuery<TResult>` + `IHotPathQueryExecutor` (F1-18) — nunca `IQueryable` crudo. Requiere `[HotPath(Justification, BenchmarkRef)]` con un benchmark real que demuestre que el patrón genérico no alcanzaba. Ver `docs/guia-hot-paths.md` |
| Que un comando tolere reintentos (doble clic, retry de red) sin duplicar su efecto | Implementar `IIdempotentCommand` (F1-22) en el comando y llamar `services.AddHttpContextIdempotencyKeyProvider()` (Shared.Infrastructure.Web) antes de `AddSharedApplication()` — el cliente envía el header `Idempotency-Key`; sin ese registro, el comando siempre se rechaza con `Idempotency.KeyRequired` |
| Notificar un hecho de negocio a otros módulos sin perderlo si el proceso falla justo después del commit | Heredar el agregado de `AggregateRoot<TId>` (Shared.Kernel) y llamar `RaiseDomainEvent(new MiEvento(...))` (F1-23) — `OutboxSaveChangesInterceptor` (Shared.Infrastructure.Persistence, ya registrado por `AddSharedPersistence<TContext>`) lo persiste como fila `OutboxMessage` dentro del mismo `SaveChangesAsync` que el cambio de negocio. No implica publicar a un broker todavía: el relay hacia Kafka es Fase 3 (ADR `docs/adr/0005-mensajeria-kafka.md`, `Proposed`) |
| Procesar un mensaje recibido de un futuro consumidor de mensajería sin duplicar su efecto ante una entrega repetida ("at-least-once") | Invocar `IInboxMessageProcessor.ProcessAsync(messageId, messageType, payload, handler)` (Shared.Application, F1-24, ya registrado por `AddSharedApplication`) antes de reconocer el mensaje ante el broker — descarta silenciosamente (`InboxProcessOutcome.Discarded`) un `messageId` ya procesado con éxito, sin ejecutar `handler` de nuevo. No implica ningún consumidor real de Kafka todavía: la suscripción al broker es Fase 3 (ADR `docs/adr/0005-mensajeria-kafka.md`, `Proposed`) |
| Exponer los endpoints estándar de liveness/readiness de un proyecto Web | `app.MapSharedHealthChecks()` (Shared.Infrastructure.Web, F1-25) en `ConfigureApplication` — mapea `/health/live` (nunca depende de SQL Server/Redis) y `/health/ready` (verifica las dependencias críticas etiquetadas `"ready"`, ya registradas por `AddSharedPersistence`/`AddSharedCaching`). Ver `docs/guia-health-checks.md` |
| Llamar a un servicio HTTP externo desde un módulo con timeout, retry, circuit breaker y bulkhead ya resueltos | `services.AddResilientHttpClient<TClient>(...)` (Shared.Infrastructure.Http, F1-26) — nunca `AddHttpClient<TClient>()` directo. Un `POST`/`PATCH` no se reintenta automáticamente salvo que se marque explícitamente seguro (`HttpRequestMessage.MarkSafeToRetry()` o header `Idempotency-Key`). Ver `docs/guia-resiliencia-http.md` |
| Versionar un endpoint HTTP nuevo o publicar un cambio breaking sin romper a los consumidores existentes | `services.AddSharedApiVersioning()` (Shared.Infrastructure.Web, F1-27) + `app.NewApiVersionSet().HasApiVersion(...)...Build()` sobre el `MapGroup` del módulo, con `.HasApiVersion(...)`/`.MapToApiVersion(...)` por endpoint — versión siempre en la ruta (`/api/v1/...`), nunca en un header. Ver `docs/guia-versionado-api.md` y `samples/Sample.Api/Productos/ProductosModule.cs` |
| Generar el contrato OpenAPI de un proyecto Web (uno por versión de API) | `services.AddSharedOpenApiForApiVersion(majorVersion)` + `app.MapOpenApi()` (Shared.Infrastructure.Web, F1-28) — anotar cada endpoint con `.Produces<T>()`/`.ProducesProblem()`/`.ProducesValidationProblem()` para que las respuestas de error (RFC 7807) queden correctamente tipadas. Ver `docs/guia-openapi.md` y `samples/Sample.Api/Productos/ProductosModule.cs` |
| Autenticar contra un IdP externo OIDC/OAuth2 (Keycloak u otro proveedor conforme al estándar) en vez del JWT propio | `services.AddSharedOidcAuthentication(configuration)` (Shared.Infrastructure.Security.Oidc, F2-01) — configura `Authority`/`Audience` desde la sección `"Oidc"`; cambiar de proveedor es solo cambiar esos valores de configuración. Mutuamente excluyente con `AddSharedSecurity` (JWT propio) dentro del mismo proyecto: ambos registran el esquema `"Bearer"`. Ver `docs/guia-oidc-adapter.md` y ADR `docs/adr/0004-identidad-idp-oidc-oauth2.md` |
| Evitar que `IPermissionEvaluator`/`[RequirePermission]` consulten SQL Server en cada request | `services.AddSharedPermissionCache(options => ...)` (F2-09, Shared.Infrastructure.Security.Permissions), llamado DESPUÉS de `AddSharedSecurity`/`AddSharedOidcAuthentication` — decora `IPermissionService` con L1 (memoria)/L2 (Redis, si está configurado) reutilizando `HybridCache`/`ITenantAwareCache` (F1-16), TTL 60s por defecto. Después de cambiar el rol de un usuario o los permisos de un rol, invalidar explícitamente con `IPermissionCacheInvalidator.InvalidateUserAsync`/`InvalidateRoleAsync` (o los overloads de `RoleManagerPermissionExtensions.AddPermissionAsync`/`RemovePermissionAsync` que reciben el invalidador) — sin invalidar, la entrada sigue vigente hasta el TTL, nunca indefinidamente. Ver `docs/guia-rbac-2.md` |

## Testing

- Un test que depende de Docker (SQL Server, Redis) va en una carpeta `Integration/` y su nombre de clase/namespace debe contener `Integration` — el filtro `FullyQualifiedName!~Integration` de CI y de uso diario depende de esa convención.
- Reutilizar `SqlServerContainerFixture`/`RedisContainerFixture` de `Shared.Testing`, no crear una copia local — ver Fase 7 para el porqué.
- Un test de integración usa `fixture.BuildIsolatedConnectionString(prefijo, nombreDeTest)` para que cada test tenga su propia base de datos dentro del mismo contenedor.
